# EOS Baseline 结果解读与指标指南

本文对应当前的 `baseline_eos_v1`，以及它的完整 validation 结果：

```text
验证样本数：3360
训练 epoch：10
eos_loss_weight：1.0
answer_nll：2.9859
exact_match：10.86%
generation_failure_rate：0.03%
verifier correct：355
verifier incorrect：1932
verifier unsupported：890
verifier invalid：183
```

这次结果已经说明 EOS 训练有效地解决了“生成一直不结束”的工程问题，但还不能说明模型已经有很强的数学能力。下面分别解释 `unsupported`、训练是否继续，以及是否开始 fixed codebook。

## 1. `unsupported` 到底是什么意思？

`unsupported` 是评测器的状态，不是模型的“答错”标签。当前 verifier 只对一部分类型实现了安全规则：

| answer_type | 当前处理方式 |
|---|---|
| `integer` | 严格整数解析，完全相等才 correct |
| `decimal` | `Decimal` 精确比较 |
| `fraction` | `Fraction` 精确比较 |
| `boolean` | true/false/yes/no 显式映射 |
| `symbol`、`option_choice` | NFC/空白归一化后的字符串比较 |
| `expression` | `unsupported` |
| `number_list` | `unsupported` |
| `symbolic_list` | `unsupported` |
| `time` | `unsupported` |
| `base_number` | `unsupported` |

完整 validation 中的 890 个 unsupported 分布是：

```text
expression      546
number_list     226
base_number      27
symbolic_list    60
time             31
```

因此不能写成“模型有 890 道题答错”。更准确的说法是：**890 道题当前没有获得经过批准的语义判定规则**。

例如某个 expression 的模型输出可能和 gold 文本完全相同，但 verifier 仍然返回 unsupported，因为项目目前没有安全的表达式等价判断器。这就是为什么评测 JSON 同时保存 `exact_match` 和 `verifier_status`。

### 现在是否必须立刻解决 unsupported？

不需要为了继续基线训练而立刻修改 verifier。当前最稳妥的做法是：

1. 继续报告总体 exact match；
2. 公开 `unsupported` 数量和按类型分布；
3. 单独报告已经有 verifier 的类型；
4. 不把 provisional verifier accuracy 称为最终语义准确率。

如果后续要完善 verifier，建议顺序是：

1. `number_list`：严格解析分隔符、元素顺序和整数/小数规则；
2. `base_number`：明确进制，不按普通十进制处理；
3. `time`：明确时间格式和进位规则；
4. `symbolic_list`：先定义列表元素的安全比较方式；
5. `expression`：最后再考虑受限符号语法和等价性。

每增加一种规则，都应加入正确、错误、格式错误和恶意输入测试。不要为了提高数字而把 unsupported 直接当成 incorrect 或 correct。

## 2. 为什么 integer 表现也一般？

完整 validation 中 integer 是 1570 条：

```text
integer correct：131 / 1570 = 8.34%
```

这比 100 条 smoke evaluation 中的数字更可信，因为 100 条样本恰好有 80 条 integer，不能代表完整验证集。当前模型确实还没有学好整数题，主要可能有几个原因：

- 30M 参数模型只训练了 10 epoch，训练预算仍然偏小；
- answer-only 任务要求模型直接从题目映射到答案，没有过程监督；
- 数据包含很多不同数学模块，任务分布很复杂；
- 当前学习率、batch size 和模型规模还没有做系统消融；
- 目前只有最终 checkpoint，没有逐 epoch 的 train/valid 曲线，无法判断是欠拟合、优化停滞还是泛化问题。

因此不要因为 integer 准确率低就立刻增加层数或扩大模型。先把训练预算和评测协议固定下来，建立可比较的 baseline。

## 3. 训练 loss 还在下降，要不要继续训练？

建议分成“研究基线”和“追求最好分数”两个概念：

### 作为研究基线

**建议先把 10 epoch 固定为第一版 baseline 预算。** 后续的 `fixed`、`random` 等对照都使用相同的 10 epoch、seed、batch size、学习率和 EOS loss。这样比较时，差异更可能来自 codebook，而不是训练时间不同。

不要一边让 direct baseline 继续训练到 30 epoch，一边只训练 fixed 10 epoch，然后比较两者准确率；这不是公平对照。

### 作为模型质量实验

如果目标是尽量提高模型分数，可以继续训练，但需要记录每个 epoch 的：

- train answer loss；
- valid answer NLL；
- valid exact match；
- generation failure rate；
- 每种 answer_type 的结果。

只有在 valid answer NLL 或 exact match 仍持续改善时，继续训练才有明确依据。如果 train loss 继续降而 valid 指标不再改善，说明继续训练可能只是过拟合；如果 train 和 valid 都不降，则应先检查学习率、loss/mask 或数据，而不是盲目增加 epoch。

当前 `baseline_eos_v1` 的 manifest 只记录最终状态，没有完整 loss 曲线，所以现在不能严谨地断言“继续训练一定有用”或“一定没用”。

## 4. 如何阅读评测 JSON？

一条 record 大致如下：

```json
{
  "id": "...",
  "prediction": "-3",
  "gold": "-3",
  "verifier": {
    "status": "correct",
    "method": "integer",
    "normalized_prediction": "-3",
    "reason": "exact integer arithmetic"
  },
  "finished": true
}
```

字段含义：

- `id`：数据集样本 ID。
- `gold`：数据集提供的标准答案原文，不是模型生成的内容。
- `prediction`：模型自由生成并去除协议标记后的答案文本。
- `normalized_prediction`：verifier 做 NFC/空白等保守归一化后的 prediction。它不是更“聪明”的答案，只是用于比较的规范形式。
- `verifier.status`：`correct`、`incorrect`、`invalid` 或 `unsupported`。
- `verifier.method`：本次使用的规则，例如 `integer`、`fraction`、`boolean`。
- `finished`：模型是否在 `max_new_tokens` 内生成了 `<EOS>`。

### 主要总体指标

- `answer_nll`：teacher-forcing 条件下，答案正文每个 token 的平均负对数似然；越低越好。它使用 gold answer 作为后续输入，不等同于自由生成准确率。
- `answer_log_likelihood`：整个评测集合答案正文 log probability 的总和；越接近 0 越好，但会随样本数和答案长度变化，不适合直接跨不同数据集大小比较。
- `exact_match`：保守归一化后的字符串完全一致比例。它覆盖所有答案类型，但对 expression/list 等可能过于严格。
- `verifier_status`：按 verifier 规则得到的状态计数。unsupported 和 invalid 必须单独保留。
- `generation_failure_rate`：没有及时生成 `<EOS>` 的比例。EOS=1 的 baseline 已降到约 0.03%。

### Oracle 字段怎么看？

当评测命令加入 `--oracle-k 16` 时，JSON 会另外出现 `oracle`：

- `oracle.scores`：对每个候选 Z token，用 gold 答案做 teacher forcing 后得到的答案 log-likelihood；
- `oracle.selected`：上述分数最高的 token，也就是 oracle 选中的条件；
- `oracle.mean_best_answer_log_likelihood`：所有样本各自最高分的平均值；
- oracle 内的 `prediction`、`finished`、`exact_match`：把选中的 Z token 放回输入后再自由生成的结果。

注意：`selected` 是用 gold answer 的分数挑出来的，测试时没有 gold 就不能这样选。因此 oracle 指标是“知道答案后最多能挑多好的 token”的上界分析，不是部署性能。只有在 codebook 条件训练过的 checkpoint 上，这个分析才有研究意义。

### “probability”在哪里？

当前 JSON 没有直接输出一个叫 `probability` 的字段，而是输出 log probability。可以这样理解：

```text
平均每个答案 token 的几何平均概率 = exp(-answer_nll)
整条答案序列的概率 = exp(answer_log_likelihood)
```

对 `baseline_eos_v1`：

```text
exp(-2.9859) ≈ 0.0505
```

这表示在 teacher-forcing 条件下，答案 token 的几何平均概率约为 5.05%。它不是“整道题答对概率”，也不是自由生成 exact match。

整条答案的概率通常很小，而且受答案长度影响，因此研究中更推荐报告 `answer_nll`，并同时报告 exact match 和 generation metrics。

可以用下面的命令读取已有 JSON：

```powershell
python -c "import json, math; p=r'D:\大四上\AIDR\Project\CoT_effectiveness_research\pilot\transformer\runs\baseline_eos_v1\eval_valid_full.json'; x=json.load(open(p,encoding='utf-8')); print('answer_nll=',x['answer_nll']); print('mean_token_probability=',math.exp(-x['answer_nll'])); print('exact_match=',x['exact_match']); print('failure_rate=',x['generation_failure_rate'])"
```

## 5. 历史 fixed 对照设计

当时可以创建 fixed 对照。该步骤现在已经完成：工作区的实验名为 `baseline_fixed_z000_v1`，manifest 确认它实际使用 `<Z_000>`。本节保留历史命令以说明实验协议，不代表它仍是下一步。

已核验到：

1. `baseline_eos_v1`：`codebook_mode=none`、10 epoch、EOS loss=1.0；
2. 完整 validation 结果；
3. 固定的 seed、数据 hash、模型配置和 tokenizer。

这构成了 direct 与 fixed-token 的配对验证集对照；结果与后续建议见 [04_Random实验决策与结果核验.md](04_Random实验决策与结果核验.md)。

### 推荐命令

```powershell
python -m CoT_effectiveness_research.pilot.transformer.train `
  --dataset-dir D:\大四上\AIDR\Project\mathematics_dataset\data\clean-100k `
  --tokenizer-dir D:\大四上\AIDR\Project\CoT_effectiveness_research\pilot\tokenizer\tokenizer\v1_sp_bpe_8k_seed1234 `
```

```powershell
python -m CoT_effectiveness_research.pilot.transformer.evaluate `

  --tokenizer-dir D:\大四上\AIDR\Project\CoT_effectiveness_research\pilot\tokenizer\tokenizer\v1_sp_bpe_8k_seed1234 `
  --dataset-dir D:\大四上\AIDR\Project\mathematics_dataset\data\clean-100k `
  --split valid `
  --output D:\大四上\AIDR\Project\CoT_effectiveness_research\pilot\transformer\runs\baseline_fixed_z000_v1\eval_valid_full.json `
  --codebook-mode fixed `
  --codebook-index 0
```

比较时至少放在同一张表里：

| run | codebook | epochs | EOS weight | answer NLL | exact match | failure rate |
|---|---|---:|---:|---:|---:|---:|
| baseline_eos_v1 | none | 10 | 1.0 | 2.9859 | 10.86% | 0.03% |
| baseline_fixed_z000_v1 | fixed Z_000 | 10 | 1.0 | 2.9905 | 11.73% | 0.09% |

当前实现中 fixed run 会更新整个 Transformer，而不是只训练 Z embedding。因此应把它描述为“带固定特殊 token 条件的全模型训练对照”，不要描述成“冻结主体后只学习 token”。
